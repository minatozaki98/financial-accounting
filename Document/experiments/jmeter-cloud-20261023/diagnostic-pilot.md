# Diagnostic pilot before scored measurements

On 2026-10-25, the first full p500 pilot ran on two Singapore 2 G6 Dedicated 8 GB/4 vCPU instances. Both API source images used the same pinned .NET base images; this pilot used only the **before** source commit. It was an environment check, not a scored before/after result.

The 12-minute JMeter run recorded 194,024 samples, zero HTTP errors, 500 unique and peak active threads, a hold-window p95 of 4,557 ms, and 268.955 requests/s. The predeclared concurrency validity gate **rejected** it: only 118 of 120 five-second hold bins had all 500 users; the final two bins fell to 189 and 2 active users. The JMeter thread group ended just before the declared hold finished. We therefore added a 30-second unscored shutdown buffer to all steady and soak plans and a separate drain buffer to the spike plan. All profile hashes changed before scoring.

The target host kept at least 5,549 MiB available, and neither API nor SQL recorded an OOM kill. SQL's 2 CPU container limit bound during the run; the API remained below its 2 CPU limit. The generator peaked at about 1.16 GiB JMeter memory, with CPU at 81.76% of one core at the 95th percentile and no OOM kill. The target's host swap occupancy rose to about 0.25 MiB, but this collector version did not capture swap page counters, so swap activity cannot be asserted from this run. Host swap was disabled before the next pilot.

Two earlier 2-user smoke runs found harness problems before this pilot. With the original `mode=core` default, the complex thread group skipped its work and JMeter threw a `StackOverflowError` under duration-bound looping. After `mode=mixed`, report requests returned HTTP 400 because JMeter did not append GET arguments to absolute sampler URLs. The corrected controlled profiles default to mixed mode and place synthetic report IDs in the GET URL. A fresh 2-user smoke then recorded 154 samples, zero errors, both active users, and no JMeter log errors. These corrections apply identically to both frozen source revisions.

The initial 8 GB/4 vCPU generator had apparent spare average capacity. Before scoring, it was deleted and replaced with the cheaper G6 Dedicated 4 GB/2 vCPU generator. Its repeat p500 pilot recorded a valid active-user hold: 119 of 120 five-second bins had exactly 500 users, the minimum was 496, and there were zero HTTP errors. The hold p95 was 4,637 ms and throughput was 263.73 requests/s. This confirms that the 30-second shutdown buffer keeps JMeter's end-of-run thread stop outside the scored hold.

The smaller generator nevertheless **failed the pre-scoring headroom gate**: 7.02% of its CPU-quota periods were throttled across the full run and **1.97% during the scored hold**, above the 1% hold limit for the load source. It used at most 67.82% of its 2.5 GiB container memory cap, had at least 1,659 MiB host memory available, and had no swap or OOM activity. The two diagnostic pilots' hold throughput differed by about 2%; that difference alone cannot establish a generator effect. The hold-window throttling measurement is the reason to reject the 2 vCPU generator. The same VM was resized to the G6 Dedicated 8 GB/4 vCPU tier, preserving its private IP and files; guest-reported CPU/RAM and no active swap were checked before the final pilot.

The final p500 pilot on two 8 GB/4 vCPU VMs **passed the measurement-validity gates**: 500 users were observed by ramp end, 119 of 120 five-second hold bins were exactly 500, the minimum was 498, and there were zero HTTP or JMeter-log errors. It recorded 4,530 ms hold p95 and 271.2767 requests/s; these are unscored setup observations. The generator had zero throttled CPU-quota periods in the scored hold, p95 cgroup use of 0.28 cores, peak memory at 29.52% of its 4 GiB cap, no OOM, and no host swap. The target host kept at least 5,466.9 MiB available.

The separate unscored spike timing pilot also **passed validity**: base 24/24 exact 100-user bins, peak 59/60 exact 500-user bins (minimum 498), and recovery 60/60 exact 100-user bins. All scored phases had zero HTTP errors and the JMeter log had no errors. Baseline, peak, and recovery p95 were 602, 4,318, and 696 ms; recovery-versus-base drift was 15.615%. These figures are setup observations, not before/after findings. The generator had zero peak-phase CPU-quota throttling, 0.28 effective cores at p95, 33.97% maximum memory use over the full run, no host swap, and no OOM. The target host kept at least 5,372.8 MiB available; SQL's 2 CPU quota was binding during the peak, which is part of the fixed target condition. Raw JTL, logs, and five-second host/container records are retained under ignored local evidence as `pilot-spike*`.
