# 2.18 Index Selection, Caching, and Data Correctness

The after revision changes several report data paths together. Chaudhuri and Narasayya (1997) developed and tested a workload-aware index-selection tool for Microsoft SQL Server. Their work shows why the value of an index depends on the actual SQL workload and the optimizer, including the search for useful multi-column indexes. This supports testing the two composite journal-entry indexes in this study under the same workload and database fixture, while also measuring write requests that must maintain those indexes. Their SQL Server 7.0 experiments do not establish that the exact indexes used here improve a later SQL Server version or this accounting schema.

Nishtala et al. (2013) describe how an in-memory cache can make repeated expensive database reads feasible in a large Web service, while also showing that invalidation and consistency become central design concerns. This supports measuring the account-ledger cache and testing that a posted journal entry invalidates stale ledger data. Their distributed Memcache architecture and scale are very different from this API's in-process cache; their throughput figures cannot be transferred to the financial application, and a cache speedup alone would not prove accounting correctness.

The fixed after revision combines caching, report-result reuse, removal of report snapshot writes, and SQL indexes. The JMeter experiment measures the **combined revision**. It records report-read and bulk-write latency, p95/p99 tails, errors, database growth, and CPU use, but it does not change one optimization at a time. The literature therefore explains the mechanisms and cautions, while the measured before/after results describe this implementation under its fixed workload.
