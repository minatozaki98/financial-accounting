# Post-scoring correction to active-user validity analysis

**Date:** 2026-10-25. **Scope:** analysis code and reporting rule only. The before/after application commits, Docker images, JMX workloads and hashes, VM/container caps, SQL backup, profile timings, pair order, and performance pass thresholds remain unchanged.

## Why the first rule was wrong

Protocol version 1 required at least one JTL request sample in **every** five-second scored bin to treat configured users as sustained. The third p500 baseline produced complete runs with 500 active JMeter threads and zero errors but one or two bins without a JTL sample. In `p500-r3-before-a1`, bin 405–410 seconds from test start was empty. In the clean `p500-r3-before-a3`, bins 270–275 and 345–350 seconds were empty. All other observed bins in those runs showed 500 users. At the empty intervals, the generator, API, and SQL container CPU activity dipped while Java thread count stayed near 528, and request latency rose around the gaps. The exact cause of these stalls is **unverified**.

The JMeter log provides separate, timestamped `Thread started` and `Thread finished` events. In both complete runs, 500 distinct threads started before the 120-second scored hold, and the first thread finished around 750 seconds, after the 720-second scored hold ended. Thus an empty **request** bin did not demonstrate a loss of active users. The original rule conflated request activity with user-thread concurrency and risked excluding severe stalls from the performance result.

## Corrected rule, applied uniformly

Protocol version 2 reconstructs the active thread count from the full JMeter lifecycle log and requires the exact target throughout each normal/soak scored hold. Spike base, peak, and recovery are checked separately after a five-second transition allowance. The lifecycle log must have one test anchor, unique starts, matching finishes, and no early finishes. JTL `allThreads` readings must be consistent wherever a request sample exists: at least 95% of **observed** bins exact and none below 95% of target. Missing JTL bins are counted and reported as request stalls or sampling gaps; they no longer fail concurrency by themselves. JMeter errors, host swap/OOM/memory loss, and generator headroom gates remain unchanged.

The corrected analysis was run on all **16 previously completed, accepted scored runs** across p50, p100, and the first two p500 pairs: all remained valid and their p95, p99, error rate, and throughput values were unchanged. It also passed all three phases of the unscored spike pilot. The complete but previously rejected p500 baselines `p500-r3-before-a1` and `p500-r3-before-a3` show valid lifecycle concurrency under version 2, but each remains outside the paired comparison because its matching after side was never run. `p500-r3-before-a2` remains excluded because an operator's in-run file transfer could have interfered with its generator. A new, complete repeat-3 pair is required under the amended rule; no favorable earlier baseline is selected.

This correction was made **after scored results existed** and must be disclosed with the final report. It is not a claim that empty request intervals were harmless: their effect on latency and throughput remains in the raw JTL and scored metrics. The study has three paired repeats per profile and does not claim the statistical confidence or stopping behavior of PT4Cloud (He et al., 2019). This distinction follows the reproducibility and statistical-reporting concerns of Papadopoulos et al. (2021) and the documented VM variability of Baresi et al. (2023).
